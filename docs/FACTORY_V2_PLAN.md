# Фабрика v2: автопоиск трендов, live-нарезка стримов и второй работник на сервере

> Статус выполнения: [FACTORY_V2_STATUS.md](FACTORY_V2_STATUS.md).

## Context — зачем это

Фабрика v1.0 (ветка `factory/v1`, фазы 0–8 из `AUTONAREZKA_FACTORY_PLAN.md`) умеет вести заранее заданные каналы: монитор находит новые записи, скаут и Whisper выбирают моменты, шаблон и кампания дают раскладку, баннер и геймплей, календарь выкладывает по площадкам. Вы хотите довести это до настоящей «фабрики, которая работает сама»:

1. **Сама ищет** стримы и видео по самым популярным сейчас темам, а не только по каналам из списка.
2. **Режет стримы в реальном времени**: идёт эфир, система смотрит, находит момент и сразу делает ролик.
3. **Работает на вашем сервере** (любой VPS, настраивается в приложении), чтобы можно было отправить задачи из приложения и выключить ПК. Проект не должен вредить тому, что на сервере уже работает.

Ваши решения (опрос в этой сессии):
- Сервер — второй работник: из приложения можно «передать задачи на сервер», в том числе перед выключением ПК.
- ПК с видеокартой включён **только часть суток**, поэтому серверу нужен и ночной режим на процессоре.
- Трафик сервера **безлимитный или больше 5 ТБ**, поэтому непрерывная запись эфиров допустима.
- Остаются прежние решения: Linux-цель, всё ИИ локально, интерфейс на русском, новые загрузки только с вашего согласия, права и кредит источника (`unspecified` → с одобрением).
- **Все режимы можно компоновать**: запускать одновременно или переключать между ними (потоки работы и сцены, этап 3б).

Реклама и геймплей уже работают (кампании, ротация баннеров, лента геймплея по таймкодам, отчёт): здесь их нужно только довезти до сервера.

## Требования к серверу

| | |
|---|---|
| Система | Ubuntu 24.04 (glibc 2.39), systemd, cgroup v2, доступ по ssh и пользователь с sudo |
| Железо | достаточно **2 vCPU, 4 ГБ ОЗУ, 6+ ГБ свободного диска**; видеокарта не нужна |
| Сеть | исходящий доступ к Twitch, Kick, YouTube; входящие порты демону не нужны (он ничего не слушает) |
| Чужие службы | на сервере может быть что угодно (веб-сервер, docker, VPN): установка их не трогает, см. правила G1–G9 |
| Ставится отдельно | ffmpeg, yt-dlp, Deno и модели (`fetch-tools.sh`, потом `install.sh --step tools/models`) |

Пошаговая инструкция для своего сервера: [SERVER_SETUP.md](SERVER_SETUP.md).

Вывод: сервер годится как **неусыпный лёгкий работник** (поиск, запись эфиров, чат, нарезка без перекодирования, планировщик, публикация по API) и как **медленный ночной резерв** (скаут, Whisper на малых окнах, рендер на x264). Он **не** годится для Qwen3-4B (нужно ~3 ГБ ОЗУ), для Whisper large и для Chromium на постоянной основе. Всё тяжёлое при включённом ПК идёт на видеокарту вашего ПК.

## Целевая архитектура

```
 ТРЕНДЫ / ТОП ЭФИРОВ                  СЕРВЕР 24/7 (CPU, свои лимиты)                    ВАШ ПК (с видеокартой, часть суток)
┌────────────────────┐        ┌─────────────────────────────────────────┐        ┌───────────────────────────────┐
│ Twitch Helix       │        │ discovery: кандидаты и оценка           │        │ приложение (Tauri) + то же ядро│
│ Kick  YouTube      │──────► │ live: запись HLS в кольцо, чат, звук    │        │ Whisper large, Qwen3, NVENC,  │
│ Google Trends,Wiki │        │       детектор пиков → сырой клип       │◄──────►│ браузерная публикация TikTok  │
└────────────────────┘        │ factory: те же стадии, CPU-профиль      │  SSH   │                               │
                              │ publish: календарь + API-площадки       │ канал  │ «Передать на сервер»,         │
 стримы идут сейчас ────────► │ БД SQLite своя, владелец у каждой задачи │ без    │ «Передать и выключить ПК»,    │
                              └──────────────┬──────────────────────────┘ shell  │ забирает результаты при старте│
                                             ▼                                    └───────────────────────────────┘
                                   Telegram / YouTube / Instagram (API)
```

**Принципы**
1. **Одно ядро, два узла.** Демон на сервере и приложение на ПК собираются из одного кода. У узла есть `Caps` (`gpu`, `llm`, размер Whisper, `nvenc`, `browser`); каждая стадия объявляет, что ей нужно.
2. **У каждой задачи ровно один владелец** (аренда). «Передать на сервер» = упаковать задачу (профиль, шаблон, назначения кампании, источник, стадия, слоты) и сменить владельца. Две БД не синхронизируем построчно, поэтому двойных публикаций быть не может: `publish_queue` и `calendar::send` отказываются выкладывать задачу чужого узла.
3. **Тяжёлое — на ПК, когда он онлайн; на сервере — когда ПК выключен.** Режим на канал: `сервер можно: всегда / если ПК выключен / никогда`. Серверный результат помечается качеством «CPU-профиль» (Whisper base/small, без LLM, x264).
4. **Лёгкое и постоянное — всегда на сервере**: опрос трендов и источников, запись эфиров, чат, планировщик, публикация по API.
5. **Сервер уступает.** Любая нагрузка проекта подчиняется жёстким лимитам systemd и собственному регулятору (ниже).
6. **Режимы компонуются.** Каждая возможность (мониторинг, автопоиск, live, ручная Студия, публикация, приём задач) — отдельный **поток работы**, который включается независимо; наборы потоков собираются в **сцены** с плавным переключением и правилами автопереключения (этап 3б). Режим выпуска канала (`auto|review|manual`) и размещение (`ПК|сервер|авто`) сочетаются с любым потоком.

## Правила «не навредить существующему» (обязательные)

| № | Правило |
|---|---|
| G1 | **Ничего существующего не меняем**: чужие службы (веб-сервер, docker, VPN), ufw/iptables, fail2ban, `/etc/ssh/*`, чужие каталоги в `/opt` и `/home` не трогаем. Создаём только новое с именем `avtonarezka*`. Соседние серверы из `known_hosts` не используются. Остановка или изменение чужих контейнеров и служб проектом не выполняется вообще |
| G2 | **Отдельный системный пользователь** `avtonarezka` (nologin, без sudo, без docker-группы). Бинарники в `/opt/avtonarezka`, данные в `/var/lib/avtonarezka`. Демон **ничего не слушает**, firewall не меняем |
| G3 | **Лимиты systemd** (`avtonarezka.slice` и юниты): `CPUWeight=10`, `CPUQuota=100%` (максимум половина машины), `Nice=19`, `IOSchedulingClass=idle`, `IOWeight=10`, `MemoryHigh=1100M`, `MemoryMax=1400M` (на сервере с большим запасом памяти можно поднять), `MemorySwapMax=0`, `TasksMax=300`, **`OOMScoreAdjust=1000`** (при нехватке памяти убивают нас первыми, а не xray), плюс `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `NoNewPrivileges`, `ReadWritePaths` только на свои каталоги |
| G4 | **Жёсткий потолок диска**: образ ext4 на 4 ГиБ в `/var/lib/avtonarezka.img`, монтируется собственным unit (не `/etc/fstab`). Дополнительно: если на `/` свободно меньше 3 ГиБ, демон ставит всё на паузу и чистит свои кольцевые буферы |
| G5 | **Регулятор нагрузки в самом демоне**: читает `/proc/pressure/{cpu,memory,io}` и `MemAvailable`. При `cpu some avg10 > 10%`, `memory some avg10 > 3%` или доступной памяти < 700 МиБ тяжёлые задачи замораживаются (`SIGSTOP`/`SIGCONT` на ffmpeg), новые не стартуют. Одновременно максимум 1 кодирование и 2 live-сессии |
| G6 | **SSH только через ограниченный ключ.** Менять sshd запрещено G1, поэтому новый отдельный ключ добавляется одной строкой в `authorized_keys` пользователя входа (`--login-user`) с `restrict,command="/opt/avtonarezka/bin/avtoctl-gate"`: без shell, без проброса портов, только список разрешённых глаголов, исполняется от `avtonarezka` через узкое правило в **новом** файле `/etc/sudoers.d/avtonarezka`. Клиент: `BatchMode`, `IdentitiesOnly`, **предохранитель: после 2 неудачных входов подряд приложение перестаёт пытаться** (иначе fail2ban забанит ваш IP на час) |
| G7 | **Установка и откат одной командой.** `install.sh` и `uninstall.sh` идемпотентны: пользователь, каталоги, образ, юниты, строка ключа, sudoers. До и после снимок состояния (`ss -tlnp`, `systemctl`, `docker ps`, `iptables-save`, SHA-256 `/etc/{nginx,ssh,fail2ban,docker,ufw}`, `free`, `df`) и `diff`: любое расхождение вне `avtonarezka*` = стоп. Изменения, сделанные самим владельцем сервера в процессе (его контейнеры, конфиги), сравнение покажет: их надо отличать от изменений проекта вручную |
| G8 | **Каждое изменение сервера и каждая загрузка — только после вашего явного «да»**: с перечнем файлов, источником и размером. Первая установка идёт с пошаговыми подтверждениями |
| G9 | **Приёмка «не навредили»**: до/во время/после нагрузочного прогона сравниваем load, PSI, OOM в `dmesg`, `docker ps` (uptime контейнеров), `NRestarts` сервисов и время ответа локального nginx. Критерий: без OOM, без рестартов чужих сервисов, `cpu some avg10 < 10%` |

## Этапы

Размеры: **S** 1–2 дня, **M** 3–5 дней, **L** 1–2 недели, **XL** 2–3 недели чистой работы.

### Этап 0 — Страховка и разведочные замеры (S)
- Закоммитить текущее рабочее дерево отдельным коммитом-«точкой отката» (**только с вашего согласия**), завести ветку `factory/v2`.
- Положить этот план в `docs/FACTORY_V2_PLAN.md`, обновить `FACTORY_REMAINING.md` ссылкой.
- Мини-разведки без изменений сервера (результат определяет детали этапов 4–5): `yt-dlp` листинг и `-g` для Twitch/Kick/YouTube с вашего ПК; каталог ссылок `docs.kick.com` (официальный `livestreams`, права токена); Twitch VOD идущего эфира (скачивание секции, пока эфир идёт); реклама в Twitch HLS.

### Этап 1 — Безголовое ядро: демон без окна, видеокарты и D-Bus (L)
Опора: разведка показала, что `analyze/*`, `render/*`, `sources/*`, `publish/{telegram,youtube,instagram,schedule,oauth}`, `tiktok/api`, `db.rs` уже не зависят от Tauri; сильная связка только в `factory/mod.rs`, `drafts.rs`, `publish_queue.rs`, `publish/calendar.rs`, `analysis_cmds.rs`, `analytics/*`, `operations/*`.
1. **Feature `desktop`** (по умолчанию включён): `tauri`, `tauri-plugin-dialog`, `webkit2gtk`, `cairo-rs`, трей и `dev_tools` становятся optional. Сборка демона: `--no-default-features --features headless` (без `gpu-probe`, то есть без Vulkan; то же для `llm-worker`).
2. **`Ctx`** вместо `AppHandle` в ядре: `Ctx { state: Arc<AppState>, bus: EventBus }` с теми же `.state()` и `.emit()`; в десктопе строится поверх `AppHandle`, в демоне — поверх `tokio::sync::broadcast`. Замена механическая, модуль за модулем по «разрезу» от самых слабо связанных; 454 теста остаются зелёными после каждого шага. `tauri::async_runtime` → `tokio`.
3. **Мелкие развязки**: `kv_get/kv_set` из `drafts.rs` в `db.rs`; `db.rs:539` не должен вызывать `drafts::load_defaults`.
4. **Секреты**: вариант `File` в `tiktok/secrets.rs` (AEAD-шифрование, ключ из systemd credentials, права 0600). Остальные ~25 вызовов не меняются. Вход OAuth (YouTube/TikTok API) выполняется на ПК, токены переносятся в серверное хранилище по каналу (на сервере нет браузера).
5. **Бинарники** `avtonarezka-daemon` (цикл фабрики без UI) и `avtoctl` (клиент-сервер по stdio: `status`, `submit`, `pull`, `events`, `cancel`, `ping`). Протокол строк JSON с чанками файлов, возобновляемый, с SHA-256 на каждый кусок.
6. **Сборка под Ubuntu 24.04** (glibc 2.39): в контейнере `ubuntu:24.04` на ПК (podman/docker, проверить наличие) или `cargo-zigbuild`. Без Vulkan, `libx264`-путь рендера и CPU-путь Whisper уже есть (`render/filter.rs:504`, `analyze/speech.rs:32`).
- Файлы: `src-tauri/Cargo.toml`, `src-tauri/src/{lib,state,db}.rs`, `factory/*`, `drafts.rs`, `publish_queue.rs`, `publish/calendar.rs`, `analysis_cmds.rs`, `tiktok/secrets.rs`, новые `src-tauri/src/bin/{avtonarezka-daemon,avtoctl}.rs`.
- Проверка: `cargo test` без регрессий; `cargo build --no-default-features --features headless` без Tauri/GTK в `cargo tree`; демон локально на ПК с тестовой БД проходит `tests/pipeline_e2e.rs`-подобный сценарий без окна; `npx tsc --noEmit`, `npm run build`, обычное приложение запускается как раньше.

### Этап 2 — Сервер: песочница и мост (M)
1. Скрипты `deploy/server/{install,uninstall,preflight,postflight}.sh` и юниты `avtonarezka.slice`, `avtonarezka-daemon.service`, `avtonarezka-data.mount` (параметры G2–G7). Ключ `~/.ssh/avtonarezka_ed25519` создаётся на ПК, на сервер уходит только публичная часть.
2. **Установка на сервер пошагово, с вашими «да»**: пользователь и каталоги → образ диска → юниты → строка ключа и sudoers → бинарники. Загрузки (названия, источники и размеры согласуем перед каждой): статический ffmpeg с libx264 и libass, `yt-dlp`, `deno`, при желании `streamlink`, модели Whisper base/small q5, YAMNet, YuNet. Предварительная оценка: утилиты 250–350 МБ, модели 0,3–0,5 ГБ.
3. **Каналу ПК↔сервер**: `ssh -o BatchMode=yes … avtoctl-gate` из приложения; фоновая «связь с сервером» в `TopBar` (чип как у yt-dlp): онлайн/офлайн, нагрузка, диск, версия.
4. **Проверка G9**: пустая установка → «привет-задача» → нагрузочный прогон (2 фейковых эфира + 1 рендер) под наблюдением PSI → `postflight` diff без расхождений.
- Проверка: `postflight` показывает ноль изменений вне `avtonarezka*`; `uninstall.sh` возвращает сервер к снимку до установки (проверяется diff).

### Этап 3 — «Передать на сервер» и «Передать и выключить ПК» (L)
1. **Модель узлов**: таблицы `nodes`, `leases`; поле `owner_node` у `factory_items` и `publications`; миграция V17 (в транзакции, с резервной копией, как существующие).
2. **Упаковка задачи** (`node/pack.rs`, чистая функция + тесты): JSON с профилем канала, снимком шаблона и стиля, назначениями кампании, правами/кредитом, источником, стадией, выбранными моментами, подписями, слотами календаря. Идемпотентна по `pack_id`.
3. **Комплект ресурсов** (`node/kit.rs`): баннеры, шрифты, **геймплей-фоны, пережатые до нижней половины кадра 1080×960 (~3 Мбит/с, 10 мин ≈ 220 МБ)**, не более ~1 ГБ суммарно; сверка по хэшам, догрузка недостающего. Лента фона по таймкодам (`gameplay.rs`) работает на сервере без изменений.
4. **CPU-профиль на сервере**: те же шаблоны и фильтры ffmpeg (`render/filter.rs`), x264 `veryfast`, Whisper base/small q5 **только на горячих окнах**, **без LLM**: заголовок и хэштеги по правилам (частотные слова из речи, `caption/generate.rs` получает не-LLM путь). Качество помечается в QC. Канал может требовать «только GPU».
5. **Маршрутизация**: если ПК онлайн и свободен — стадия идёт на ПК; иначе, по правилу канала, на сервер. Владелец меняется только на границах стадий.
6. **UI**: панель «Сервер» (статус, нагрузка, диск, список задач на сервере, журнал), у карточек Фабрики значок узла, диалог «Передать на сервер…» (что именно, по каждой задаче можно снять галочку), кнопка **«Передать и выключить ПК»**: загрузка паков и ресурсов → сервер подтверждает приём с проверкой хэшей → обратный отсчёт 60 с → `systemctl poweroff`. Пока не всё принято, ПК не выключается. При запуске приложение само забирает финалы, журнал и статусы публикаций.
7. **Публикация с сервера** (первая часть): календарь и API-площадки Telegram/YouTube/Instagram на сервере. Правило: TikTok через браузер остаётся на ПК, пока не пройдёт отдельный эксперимент (этап 6).
- Проверка: юнит-тесты упаковки/аренды/маршрутизации; e2e на двух процессах (имитация «ПК» и «сервер» с поддельными площадками): передача → отключение «ПК» → публикация по слотам → возврат результатов; убийство демона посреди работы без двойных публикаций; живой прогон на настоящем сервере с короткими видео.

### Этап 3б — Режимы: потоки и сцены (M–L)
Цель: любые режимы можно включать вместе, переключать на лету и сочетать по правилам.
1. **Три независимые оси** (что значит «режим»):
   - **Поток работы** (что делает фабрика): `studio` (ручная Студия), `monitor` (новые записи каналов), `discovery` (автопоиск трендов), `live` (live-нарезка), `publish` (календарь и выкладка), `offload` (приём задач от ПК на сервере). Каждый включается независимо.
   - **Режим выпуска канала** (как далеко идём без вас): `auto | review | manual`, уже есть, остаётся на канал и сочетается с любым потоком.
   - **Размещение** (где считается): `ПК | сервер | авто`, на поток и на канал.
   Итог: матрица «поток × канал × режим выпуска × размещение». Пример: канал А — live + auto на сервере; канал Б — monitor + review на ПК; тренды — discovery только в Inbox; одновременно.
2. **Поток = плагин** (`src-tauri/src/workflows/`): `trait Workflow { id, requires: Caps, budget, start, stop(graceful), status }`. `monitor`, `publish` и ручная Студия оборачиваются без переписывания, `discovery` и `live` (этапы 4–5) сразу пишутся как потоки. Таблицы `workflow_state`, `scenes`, `scene_rules`, миграция в транзакции.
3. **Одновременная работа**: общий планировщик ресурсов поверх существующих дорожек (`factory/resources.rs::Lane`, `ml_gate`, `youtube_slots`, `browser_gate`) плюс новые `live_slots`, `discovery_budget` и серверные лимиты CPU/диска/трафика из G3–G5. Чистая функция `plan(сцена, узлы, нагрузка) -> действия` (покрывается тестами). Приоритеты: `live` > ручная Студия (вы ждёте) > тренды > бэклог записей > фон. Видеокарта одна (`ml_gate`, 4 ГБ: LLM и Whisper не вместе): live-клип обходит очередь на границе стадии, тяжёлый скаут VOD ставится на паузу и продолжается (пауза на диск уже есть). Несовместимые комбинации интерфейс показывает серыми с причиной, а не ломает молча.
4. **Сцены** — именованные наборы потоков с параметрами и бюджетами: «День за ПК», «Ночь на сервере», «Только live», «Экономия», «Пауза всего». Переключение **плавное**: новые задачи не берутся, текущие доходят до границы стадии (или замораживаются), затем стартуют потоки новой сцены. Ничего не теряется (состояние в БД), откат на прошлую сцену одной кнопкой.
5. **Автопереключение по правилам** «если → то»: по времени суток, по состоянию ПК (онлайн/офлайн → сцена), по нагрузке сервера (PSI высокий → `live` снижается до одного эфира), по месту на диске, по событию (стример вышел в эфир → включить live для него). Ручное переключение закрепляет сцену на N часов, чтобы правила её не дёргали. «Передать и выключить ПК» (этап 3) = переключение на сцену «Ночь на сервере» + передача.
6. **UI**: экран **«Режимы»** (переключатели потоков, матрица «поток × канал», список сцен, правила, журнал переключений), быстрый переключатель сцен в `TopBar`, в панели «Сервер» видно, какие потоки идут там.
- Проверка: юнит-тесты `plan()` (приоритеты, конфликты, бюджеты, закрепление); e2e: два потока одновременно (`monitor` + `live` на фейках) под лимитами; смена сцены посреди работы без потерь и дублей; правило «ПК выключился → сцена на сервере» и обратно; смена сцены с остановкой демона; скриншоты экрана «Режимы» в духе приложения.

### Этап 4 — Автопоиск: радар трендов (L)
Модуль `src-tauri/src/discovery/` рядом с `factory/monitor.rs`; работает на сервере, умеет и на ПК. Регистрируется как поток `discovery` (этап 3б).
1. **Провайдеры** (каждый необязателен, за общим трейтом, у каждого проверка здоровья и свой бюджет):
   - Twitch Helix: `Get Streams` (топ по зрителям, язык `ru`), `Get Top Games`, `Get Clips` по играм за 24 часа (клипы уже отобраны зрителями). Расширяем `TwitchApi` в `analyze/clips.rs`: кэш токена, пагинация. Нужны бесплатные Client ID/Secret.
   - Kick: официальный `GET /public/v1/livestreams` (сортировка по зрителям; проверить документацию и способ получить токен), запасной путь `kick.com/api/v2`, который с сервера сейчас отвечает.
   - YouTube: Data API `videos.list chart=mostPopular` (1 единица квоты; после июля 2025 даёт только музыкальные/игровые/кино-чарты, проверить), `search.list` по живым (100 единиц, бюджет ≤40 в сутки) и `ytsearchdate:` через yt-dlp без квоты.
   - Темы: Google Trends RSS для RU, Wikipedia most-read; Reddit/TikTok Creative Center только как необязательные хрупкие источники.
2. **Снимки и скорость роста** в таблице `discovery_snapshots` раз в 5 минут: оценка идёт по приросту зрителей и скорости набора просмотров, а не по абсолютным цифрам.
3. **Оценка** — чистая функция `trend_score` (z-оценки роста, совпадение с темой, близость к вашему списку каналов и категорий, штрафы за уже обработанное, язык, длительность, отсутствие разрешения), тесты на золотых данных.
4. **Кандидаты**: таблица `discovery_candidates` (вид `live|vod|clip`, платформа, ссылка, метрики, оценка, «почему» одной строкой). Экран **«Тренды»**: карточки с причиной («+340 % зрителей за 30 мин, категория X»), принять, отклонить, «следить за каналом». Принятый кандидат становится `source_item` с профилем канала-«песочницы».
5. **Автопринятие** только по правилам: оценка ≥ порога **и** (канал в белом списке **или** `permission ∈ {owned, agreed}`); лимиты: новых задач в сутки, ГБ в сутки.
6. **Закрыть дыру прав**: `permission` реально проверяется в `factory/mod.rs` (автоодобрение) и перед постановкой в календарь. `unspecified` → принудительно `review`, строка кредита в подписи, публикация только после вашего одобрения в Inbox. Это не отменяет ваш выбор, но не даёт полностью автоматически выкладывать чужое без отметки.
- Проверка: юнит-тесты провайдеров на записанных ответах; e2e с поддельным Helix/Kick/YouTube; `#[ignore]`-тест с живыми запросами (ключи в связке); экран «Тренды» на реальных скриншотах (`/dev/snapshot`), без `backdrop-filter` в сетках.

### Этап 5 — Live-нарезка (XL)
Модуль `src-tauri/src/live/`. Основной режим — сервер (24/7); на ПК тот же код для разовых сессий. Регистрируется как поток `live` (этап 3б): работает одновременно с остальными потоками и по приоритету обходит очередь.
1. **Сессия слежения**: таблицы `live_sessions`, `live_moments`; запуск вручную («следить за этим эфиром») или по трендам из этапа 4 и по списку каналов. Максимум 2 эфира одновременно (G5), счётчик трафика и места на экране «Эфиры».
2. **Запись**: адрес HLS получаем через yt-dlp, ffmpeg копирует без перекодирования в **кольцо сегментов** (`-c copy -f hls -hls_time 4 -hls_list_size 300 -hls_flags delete_segments+program_date_time`, ≈20 минут, ~0,9 ГБ на эфир при 6 Мбит/с). Переподключение с отступом, учёт рекламных вставок Twitch (проверить в этапе 0, запасной путь — streamlink), конец эфира.
3. **Живой чат**: Twitch IRC по websocket анонимно (`justinfan…`, чтение), Kick через публичный websocket (неофициально, изолировать и мониторить), YouTube live chat разбором innertube или через `yt-dlp` в файл. Своих токенов нет, ничего не пишем в чат.
4. **Уровень звука**: берём из записанных сегментов (RMS и скачок, `analyze/audio.rs::rms_db`), второго подключения не делаем.
5. **Детектор** — чистая функция `detector::step(state, sample) -> Option<Trigger>` с тестами на синтетике: робастная z-оценка за 10 минут по частоте сообщений, доле смайлов, числу уникальных авторов, звуку и подсказкам («клип», `KEKW`, `LUL`, «ахах»); порог и гистерезис, пик отслеживается до спада, окно `[пик−30 с … конец пика+10 с]` (20–90 с), охлаждение 60 с, потолок роликов в час на эфир. Пороги настраиваются в профиле канала.
6. **Резка**: `ffmpeg -c copy` из кольца (секунды, почти без CPU) → файл сырого клипа → `source_items` вида `live_clip` и сразу `selecting/drafting` (стадии `fetching/scouting` уже выполнены). Whisper только на этом клипе для субтитров. Режим канала (auto/review/manual) и QC работают как раньше. Переиспользуем `source_segments` с подменой пути в `drafts::build_job` (`drafts.rs:437`) и `factory/media.rs::segment`.
7. **Конец эфира**: обычная обработка записи подхватывает остальное, окна ±30 с вокруг уже вырезанных live-клипов пропускаются (без дублей).
8. **Задержка**: пик → готовый вертикальный ролик ≈ 2–3 мин при включённом ПК, ≈ 5–10 мин на сервере (оценка, замерить).
9. **Экран «Эфиры»**: живая лента сигналов (чат/звук/оценка), метки найденных моментов, кнопки «вырезать сейчас» и «игнорировать», ручная доводка границ.
- Проверка: фейковый эфир (`ffmpeg -re` из тестового видео с известным всплеском звука в известной секунде) + фейковый IRC-сервер с всплеском сообщений → клип с верной границей, без дублей и при разрыве; e2e с остановкой демона; живой тест на настоящем эфире (вы выбираете стримера) в режиме `review`; замер PSI и места на сервере во время 2 эфиров.

### Этап 6 — Публикация с сервера целиком и TikTok (M)
- Ночная публикация по API с сервера: проверена в этапе 3, здесь добавляем уведомления вам (Telegram-бот: «нужна капча», «квота», «needs_check», итог ночи).
- **TikTok с сервера — экспериментально и только после отдельного решения**: нужен Chromium (загрузка «Chrome for Testing»/headless-shell в `/opt/avtonarezka`, ~150 МБ, ОЗУ 500–700 МБ под G3; главным остаётся риск капчи) и сессия аккаунта; вход с датацентрового IP может вызвать капчу и пометки аккаунта. Сначала проверка на тестовом аккаунте; при любых признаках проблем TikTok остаётся только на ПК, а готовые ролики ждут его включения.

## Риски и допущения (честно)

- **Права на чужой контент**: автопоиск берёт чужие записи; площадки могут выдавать жалобы и ограничения. Смягчаем «песочницей прав», кредитом, трансформацией и автопаузой канала по жалобам, но решение о контенте остаётся за вами.
- **Неофициальные интерфейсы** (Kick websocket/`api/v2`, Twitch GQL через yt-dlp) могут ломаться; поэтому у каждого адаптера проверка здоровья и изоляция.
- **YouTube с датацентрового IP** сейчас отдаёт страницы без бот-проверки, но может начать требовать вход; запасной путь: скачивание на ПК или cookies из вашего браузера (опция уже в плане).
- **Качество на сервере ниже** (Whisper base/small, без LLM): помечается и настраивается на канал.
- **Железо сервера слабое**: всё держится на лимитах G3–G5 и OOM-приоритете. Большие объёмы реалистичны только при включённом ПК или после апгрейда сервера.
- **Цифры времени** (скорость Whisper/x264 на 2 vCPU, задержка live) — оценки; замеряем в этапах 2 и 5 до фиксации целей.
