# План: «Фабрика контента» поверх Автонарезки (v0.3.0 → v1.0)

**Уточнение пользователя 16.11.2026: целевая система — Linux. Windows исключён из объёма v1.0: поддержка, сборки, установщик и проверки Windows не являются условиями готовности.** Прежние Windows-материалы сохраняются как история.

## Context — зачем это

Сейчас Автонарезка — отличный **инструмент для одного видео**: Импорт → Анализ → Моменты → Черновики → Финал → TikTok. Ты хочешь **фабрику**: поставил каналы/источники один раз — дальше система сама находит новые стримы и видео, режет, оформляет (раскладка, субтитры, **твой рекламный баннер**), подписывает и выкладывает по расписанию в несколько соцсетей, а ты только изредка одобряешь пачкой и смотришь отчёт.

Что ты выбрал в опросе (это опорные решения плана):

| Вопрос | Решение |
|---|---|
| Источники | Записи стримов (Twitch/Kick/YouTube Live), обычные длинные видео, **чужие реакции и стримы с вебкамерой** |
| Суть | Режешь нарезки и вставляешь **свой рекламный баннер**, всё должно быть автоматизировано |
| Площадки | TikTok, YouTube Shorts, Instagram Reels, VK Клипы / Telegram |
| Автономность | **Гибрид, режим выбирается на каждый канал** (авто / с одобрением / вручную) |
| Раскладка | **«Чужое видео + кружок/рамка с лицом»** (реакция) — рядом остаётся нынешняя «момент + геймплей-фон» |
| Объём | Не знаю — нужен запас на рост (архитектура масштабируемая, начинаем с малого) |
| Где работает | **Твой ПК, запускаешь когда нужно** (без демона/сервера; всё равно оркестратор отделяем от окна) |
| Реклама | Один баннер → **ротация с правилами** → **отчёт для рекламодателя** → **ссылка/промокод в подписи** |

Остаются в силе прежние решения из памяти: Tauri 2 + Rust, **всё ИИ локально**, интерфейс на русском, новые модели/инструменты скачиваем **только с твоего согласия**, Gemini/Antigravity не предлагаем.

## Что уже есть и чего не хватает (по разведке кода)

**Опора (переиспользуем):** конвейер анализа (громкость, сцены, YAMNet, Whisper, Qwen3-4B на Vulkan), рендер одной командой ffmpeg с NVENC (`render/filter.rs`), баннер-хромакей, субтитры по словам, «лента» фона (`gameplay.rs`), пачка со стадиями (`batch.rs`), очередь автовыкладки с паузой/лимитом/окном/пулом аккаунтов (`publish_queue.rs`, `accounts.rs`), TikTok через API и Chromium-CDP (`tiktok/*`), скачивание YouTube через yt-dlp (`youtube/*`), SQLite с миграциями V1–V9, модельный загрузчик с SHA-256 (`model_download.rs`), мок-бэкенд фронта, e2e-тесты с поддельными серверами.

**Пробелы до фабрики:**

| Область | Чего нет |
|---|---|
| Источники | Только одиночное видео YouTube. Нет Twitch/Kick, каналов, плейлистов, мониторинга новых записей, чата |
| Модель данных | Нет сущностей «канал», «шаблон», «кампания», «аккаунт-цель». Один глобальный набор умолчаний, один активный проект |
| Оркестрация | Пачка последовательная, без приоритетов/паузы/потолка, без настройки параллелизма; очередь публикации привязана к одному проекту; после перезапуска не возобновляется |
| Отбор моментов | Часовой стрим — дорого (Whisper на всё). Нет чата, лиц, реакции зала; режим «по N секунд» заявлен в README, но **не подключён** (`score::fixed_grid` вызывается только тестами); язык Whisper жёстко `ru`; веса не настраиваются |
| Раскладки | Единственная: верх + геймплей. Нет вебкамеры/кружка, нет поиска лица |
| Публикация | Только TikTok, нет абстракции платформ; нет календаря (в БД есть `publish_jobs.not_before`, в UI нет); подпись заточена под TikTok (3990–3999 знаков) |
| Реклама | Один баннер, без ротации/правил/кампаний/отчётов, ссылка не вставляется в подпись |
| Аналитика | Никаких метрик опубликованного, нет обратной связи в отбор |
| Эксплуатация | Нет блокировки сна ПК, управления диском, уведомлений, единой панели «что сейчас происходит» |

Мелкие долги, найденные при чтении (чиним в Фазе 0): режим «по N секунд» не подключён; `queue_job_resolve` и `queue_stop` в `publish_queue.rs` не обновляют/не возвращают задачи готовых роликов (`ready_id`); миграции в `db.rs` без транзакции (V9 сложная); `ass.rs` не ограничивает `split`, как `filter.rs`; TikTok-селекторы не проверены на живой странице; `gsap` и `@react-three/drei` лежат в `package.json` без использования.

## Целевая архитектура

```
 ИСТОЧНИКИ                  ФАБРИКА (оркестратор в Rust, не зависит от окна)                 ПЛОЩАДКИ
┌──────────────┐   ┌────────────────────────────────────────────────────────────────┐   ┌──────────────┐
│ Twitch  VOD  │   │ source_item ─► [скаут: аудио+прокси] ─► горячие окна            │   │ TikTok       │
│ Kick    VOD  │──►│   новая запись   сигналы: звук, чат, сцены, лицо, клипы зрителей │   │ YouTube Shorts│
│ YouTube      │   │      │            ─► [Whisper+LLM только на окнах] ─► моменты    │   │ Instagram    │
│ папка/файл   │   │      ▼                                                         │   │ VK Клипы     │
└──────────────┘   │  качаем только горячие куски в 1080p                            │   │ Telegram     │
  монитор каналов  │      ▼                                                         │   └──────▲───────┘
  (пока приложение │  черновики по ШАБЛОНУ канала (раскладка + баннер из КАМПАНИИ)    │          │
   открыто)        │      ▼            режим канала: auto │ review │ manual         │   публикатор: лимиты,
                   │  QC-проверки ─► Inbox одобрения (пачкой) ─► финал ─► подпись     │   окна, календарь,
                   │      ▼                                      (по площадке)       │   аккаунты, ретраи
                   │  календарь/слоты ─────────────────────────────────────────────► │──────────┘
                   └───────────────▲────────────────────────────────┬───────────────┘
                                   │ метрики, отчёты, подсказки весов│
                                   └──────────── аналитика ◄─────────┘
```

**Принципы**
1. **Канал = профиль**: источник + шаблон + кампания(и) + цели публикации + режим + параметры анализа + права/кредит. Всё остальное берёт настройки из профиля.
2. **Оркестратор отдельно от UI**: чистая state-machine по `source_item`, каждая стадия записывается в SQLite (переживает перезапуск), UI только подписан на события. Сегодняшний `batch.rs` — прототип; **обобщаем его, а не строим рядом третью очередь**.
3. **Ресурсные «дорожки»**: GPU-тяжёлое (Whisper, LLM) — по одному, рендер — настраиваемо, загрузки — 2. Видеопамять 4 ГБ: LLM (~3,3 ГБ) и Whisper не одновременно (сейчас так и есть, закрепляем явно).
4. **Платформа = плагин** (`trait Platform` с возможностями: лимиты подписи/длины/частоты, способ входа), TikTok становится первым реализованным плагином, без переписывания `tiktok/*`.
5. **Чистые функции там, где решения** (расписание, ротация баннеров, QC, сглаживание рамки лица, сбор команды ffmpeg) — легко тестировать, как уже сделано с `next_action` и `render::filter::build`.

**Новые сущности БД (миграции V10+, каждая в транзакции)**
`channels`, `templates` (именованные Style + вид раскладки; текущие `Defaults` переезжают в шаблон «По умолчанию»), `source_items`, `factory_items` (обобщённая замена `batch_items`, строки переносятся), `campaigns` + `campaign_banners`, `clip_campaigns` (какой ролик с каким баннером), `publications` (замена `posts` + `publish_jobs`, строки переносятся; платформа, аккаунт, внешний id, URL, состояние), `metrics`, `ad_reports` (опц.), `events` (журнал для экрана «Что происходит»).

## Фазы реализации

Размеры: **S** ≈ 1–2 дня, **M** ≈ 3–5 дней, **L** ≈ 1–2 недели, **XL** ≈ 2–3 недели чистой работы. Фазы 2, 3/4 и 5 после Фазы 1 идут по **разным областям кода** (`sources/`, `analyze/`+`render/`, `publish/`) и могут вестись параллельно в отдельных сессиях.

### Фаза 0 — Фундамент и долги (S–M)
Цель: чистая база перед ростом, без новых функций «на вид».
- Подключить **режим «по N секунд»**: `fixed_grid` → `Options`/`UiOptions` (`analysis_cmds.rs`, `analyze/pipeline.rs`) + переключатель на экране «Анализ» (`screens/Analysis.tsx`).
- **Язык Whisper**: `Options.language` в UI и «авто»; параметры анализа сохраняются (пока в `kv`, потом в профиль канала). Вывести `Weights`, `llm_top`, `llm_weight` в «Расширенные».
- Починить очередь для готовых роликов: `queue_job_resolve` (проект через `ready_videos`), `queue_stop` (возврат `queued → ready` и для `ready_id`) в `publish_queue.rs`.
- Миграции в транзакции + тесты миграций (`db.rs`), ограничение `split` в `render/ass.rs`.
- Убрать неиспользуемые `gsap`/`drei`; убедиться, что `tsc` и `cargo test` зелёные.
- **Чек-пойнт с тобой:** живой TikTok — принимает ли веб-поле 3999 знаков, селекторы Studio (`success_url`, `confirm_button`), видимость по умолчанию. Результат фиксируем в `tiktok/browser.rs`.
- Проверка: `cargo test` (новые тесты миграций и режима N секунд), `npx tsc --noEmit`, прогон на реальном окне.

### Фаза 1 — Ядро фабрики: профили, шаблоны, общая очередь (L)
Цель: «Каналы», «Шаблоны», общий экран «Фабрика» и режимы auto / review / manual. Источники пока те же (файл, ссылка YouTube).
1. **Данные**: миграции `channels`, `templates`, `factory_items`; перенос `Defaults` → шаблон «По умолчанию», `batch_items` → `factory_items` (`db.rs`, `drafts.rs` `Defaults`/`upgrade_layout`).
2. **Оркестратор** `src-tauri/src/factory/` (из `batch.rs`): стадии `discovered → queued → fetching → scouting → selecting → drafting → qc → awaiting_approval | auto_approved → rendering_final → captioning → scheduled → publishing → published → measured`, приоритеты, пауза/возобновление (вместо «Остановить = отмена»), порядок (`position` уже в БД), настройка параллелизма в UI (сейчас зашито в `state.rs`: 2 черновика, 1 финал, 2 загрузки), потолок числа роликов на источник (риск «160 финалов»).
3. **Режимы канала**:
   - `auto`: моменты со score ≥ порога и top-N на источник принимаются сами; черновики одобряются, если прошли QC; финал и расписание — сами;
   - `review`: всё готовится, но останавливается в **Inbox**; ты одобряешь пачкой;
   - `manual`: как сейчас (экраны 1–5).
4. **QC** (`qc.rs`, чистые проверки + ffprobe/ffmpeg): длительность по площадке, не тишина (`volumedetect`), нет чёрных кадров (`blackdetect`), субтитры есть, лицо найдено (для раскладки «Реакция»), размер/кодек. Провал → не отбраковка, а переход в Inbox с причиной.
5. **UI-оболочка**: боковая панель вместо одного степпера: **Фабрика** (доска: источники → в работе → Inbox → в календаре → выложено), **Каналы**, **Шаблоны**, **Кампании** (заглушка до Фазы 6), **Календарь** (до Фазы 5 — простой список), **Аналитика** (заглушка), **Аккаунты**, **Студия** (нынешние 5 шагов без изменений для ручной работы), **Настройки**. Inbox: сетка карточек, клавиши (→ одобрить, ← отклонить, A — все), как в «Моментах». Списки > 24 элементов — виртуализированные (`lib/dense.ts`).
6. **Журнал** `events` + экран «Что происходит» (последние стадии, ошибки, «нужно твоё действие»).
- Реиспользуем: `batch.rs` (стадии, prefetch), `publish_queue::next_action` (позже), `drafts::generate`/`build_job`, `Tilt`/`Toasts`/`AssetLibrary`.
- Проверка: юнит-тесты стейт-машины (переходы, восстановление после «аварийного закрытия» по образцу `recover_interrupted_jobs`), e2e на поддельных видео (`tests/pipeline_e2e.rs`-подход), реальное окно: канал в режиме auto и в режиме review на 2–3 коротких видео.
- Дизайн: обязательно смотреть **реальные скриншоты** (`/dev/snapshot`); не использовать `backdrop-filter` в сетках и диалогах (зависание WebKitGTK, см. память), свои `@keyframes` называть не `spin`.

### Фаза 2 — Источники и мониторинг (L)
Цель: «поставил канал — новые записи приходят сами».
- `src-tauri/src/sources/` (из `youtube/`): `trait Source` (`classify(url)`, `list_new(channel, since)`, `download(item, mode)`), реализации:
  - **YouTube**: канал/плейлист/прямые эфиры через `yt-dlp --flat-playlist`; снять запрет на плейлисты в `youtube/url.rs`;
  - **Twitch VOD** и **Kick VOD**: через тот же `yt-dlp` (в духе прежнего решения «системные утилиты, ничего не вшивать»; **поддержку Kick проверить** на реальной ссылке при реализации);
  - **папка** (watch-folder) для готовых файлов.
- **Монитор** (`factory/monitor.rs`): раз в N минут (пока приложение открыто) проверяет включённые каналы, новые записи → `source_items`; фильтры: мин/макс длительность, регэксп названия, «уже виденные» по внешнему id.
- **Двухпроходное скачивание** (резко снижает диск/трафик на многочасовых VOD): проход 1 — только аудио + низкое качество («прокси» для скаута); проход 2 — только «горячие окна» в целевом качестве (`yt-dlp --download-sections`; **проверить на HLS Twitch**, запасной путь — скачать целиком).
- Cookies для закрытых/платных записей — **не делаем по умолчанию**; только опция «cookies из моего браузера» для записей, доступных тебе самому.
- Политика хранения: удалять оригиналы/прокси через X дней или при превышении лимита ГБ (экран «Диск», Фаза 8).
- Проверка: `tests/youtube_e2e.rs`-подход с поддельным `yt-dlp` (новые сценарии: канал с 3 записями, повторный опрос не дублирует, режет по фильтру длительности), один `#[ignore]`-тест с реальным yt-dlp на короткой записи.

### Фаза 3 — Умный отбор для длинных записей (L)
Цель: 3–6-часовой стрим обрабатывается за разумное время и даёт лучшие моменты, а не «всё громкое».
1. **Двухуровневый анализ** в `analyze/pipeline.rs`: *скаут* по всей записи только дешёвыми сигналами (RMS, YAMNet, сцены, чат, активность камеры) → «горячие окна» (с отступами) → Whisper **только на них** → LLM на top-N. Линейная прикидка по текущей скорости (89 с видео ≈ 21 с анализа) — около 40 мин на 3 часа с полным Whisper; цель скаута — кратно меньше. **Первым шагом фазы замерить на настоящем 3-часовом VOD**, цель зафиксировать после замера.
2. **Чат как сигнал** (`analyze/chat.rs`): парсеры — Twitch (внешний `TwitchDownloaderCLI`, **ставишь ты / скачиваем с твоего согласия**, чип в `TopBar` как у yt-dlp), YouTube live-chat replay (`yt-dlp --write-subs --sub-langs live_chat`), Kick — best-effort после проверки. Фичи: частота сообщений (robust-z, как `audio::robust_z`), плотность смайлов (KEKW/LUL/OMEGALUL/Pog…), всплеск уникальных авторов. Новый вес в `Weights` (`score.rs`), по умолчанию 0 если чата нет (механизм «нет сигнала — веса пересчитываются» уже есть).
3. **Клипы зрителей Twitch** (Helix Get Clips по VOD; нужен бесплатный Client ID/Secret; поле `vod_offset` **проверить**) — сильный сигнал «зрители сами это вырезали».
4. **Активность камеры** (после Фазы 4): движение/мимика в рамке лица как «реакция».
5. **Качество выбора**: разнообразие (не 10 моментов из одной минуты), дедуп похожих, срез тишины в начале клипа, «хук» в первые 3 с от LLM, язык по профилю канала (русский/авто).
6. **UI**: веса и пороги в профиле канала; в «Моментах» — **тепловая карта сигналов по времени** (чат/звук/смех над таймлайном) и ручная доводка границ.
- Проверка: юнит-тесты парсеров чата и новой кривой; `analyze` e2e на синтетике (всплеск в известной точке попадает в top); бенчмарк `#[ignore]` на 3-часовом файле; сравнение «скаут» vs «полный Whisper» на одном видео (совпадение top-10 моментов — метрика качества).

### Фаза 4 — Раскладка «Реакция» с кругом лица (L)
Цель: «чужое видео + кружок/рамка с лицом» как шаблон канала.
1. **Поиск лица**: YuNet (ONNX, MIT, ~230 КБ) через уже подключённый `tract-onnx` — `analyze/face.rs`; модель скачиваем через `model_download.rs` **с твоего согласия**, SHA-256 закрепляем. Семплируем кадры (2/с, как `analyze/video.rs`), берём **медианную рамку** по записи (камера стримера стоит на месте), сглаживание/гистерезис — чистая функция.
2. **Профиль камеры на канал** (`channels.cam_rect`, нормированные координаты): при первом видео канала авто-найденная рамка показывается на кадре-превью, ты двигаешь/подтверждаешь один раз; дальше переиспользуется; на каждом видео проверка «лицо всё ещё там?», иначе → Inbox с причиной.
3. **Рендер**: в `render/types.rs` — `Layout { GameplayStack (как сейчас), ReactionPip, ReactionStack }`, в `render/filter.rs` `build()` диспетчеризует на свою функцию (сегодняшняя остаётся нетронутой). Круг: маска через `geq`/PNG-маску + `alphamerge`, кольцо-обводка, тень, небольшой зум по лицу, позиции-пресеты (на стыке слева/по центру, правый нижний угол…), размер в %, «поп-ин». Основной контент — как `TopFit::Contain/Fill`; низ — геймплей-фон **или** без него (развёртка на весь кадр) — **выбираешь в шаблоне; до реализации покажу 2–3 макета на реальном кадре**.
4. Баннер на «климаксе» остаётся: верх замирает; **кружок по умолчанию замирает вместе с верхом** (опция «продолжает играть»). Субтитры и «Часть N» подстраиваются под раскладку (`y_pct` по умолчанию из шаблона).
5. **Быстрый предпросмотр шаблона**: команда `layout_preview(channel, t)` — один кадр через ffmpeg `-frames:v 1` и отрисовка в редакторе шаблона; галерея шаблонов с живыми превью (визуал!).
6. Деградация: лица нет → кружок не рисуется, ролик помечается для Inbox.
- Проверка: пиксельные e2e по образцу `tests/render_e2e.rs` (синтетический источник с цветным прямоугольником «камеры» → в итоге в ожидаемой позиции круг нужного цвета, углы маски прозрачны); юнит-тесты `build()` для новых раскладок; тест `face` на твоём реальном кадре (`#[ignore]`); реальное окно + скриншоты шаблонов.

### Фаза 5 — Мультиплатформенная публикация и календарь (XL)
Цель: один готовый ролик уходит в нужные аккаунты нужных площадок по календарю.
1. **Слой платформ** `src-tauri/src/publish/`: `trait Platform` + `Caps` (макс. заголовок/подпись/хэштеги/длительность, суточный лимит по умолчанию, умеет ли расписание, вход), таблица `publications` (миграция с переносом `posts` и `publish_jobs`), секреты по аккаунтам в связке ключей (обобщить `tiktok/secrets.rs`), общий OAuth-loopback (по образцу `tiktok/oauth.rs`). `tiktok/*` остаётся и подключается как плагин.
2. **Движок подписей** `caption/` (обобщение `analyze/describe.rs`): `CaptionSpec` на площадку, шаблон `{название} {кредит} {ссылка} {промокод} {хэштеги}`; **Уточнение пользователя 15.11.2026:** текст необязателен и вводится вручную — общий для всех готовых роликов или отдельный для каждого. Минимума длины TikTok нет; верхний предел 3999 UTF-16 сохраняется. Локальная LLM генерирует только хэштеги. Одинаковый ручной текст разрешён.
3. **Коннекторы по возрастанию риска**:
   **Уточнение пользователя 16.11.2026:** доступы Telegram/VK подключаются позднее через приложение. В «Аккаунтах» нужны явные переходы и инструкции; отсутствие подключения не блокирует локальный анализ и монтаж. Живые проверки отложены, VK uploader по-прежнему отдельный незавершённый пункт.
   1. **Telegram** (Bot API `sendVideo`, бот — админ канала; самый простой, подтверждает абстракцию);
   2. **YouTube Shorts** (Data API v3, загрузка resumable, `status.publishAt` для расписания). **Проверить при реализации:** актуальная квота `videos.insert` (источники расходятся: ~1600 vs ~100 единиц) и снимается ли «private-only» для непроверенного проекта — результат аудита определяет, идёт ли путь через API или через браузер (YouTube Studio);
   3. **Instagram Reels** (Graph API: Business/Creator-аккаунт + страница Facebook + приложение Meta в режиме разработки для своих аккаунтов; контейнер `REELS` → resumable-загрузка на `rupload.facebook.com` → опрос `status_code` → `media_publish`; лимит публикаций за 24 ч — **сверить с `content_publishing_limit`**, в документации встречаются 50 и 100);
   4. **VK Клипы**: метод `shortVideo.create` (подтверждения в официальной документации не нашёл — **сначала разведка**, запасной путь — браузер);
   5. **Браузерный драйвер** (обобщить CDP из `tiktok/browser.rs`) как запасной путь там, где API закрыт; правило остаётся: капча → пауза и ждём человека.
4. **Планировщик**: обобщить `publish_queue::next_action` — лимит, пауза и окно **на пару аккаунт×площадка**, ротация аккаунтов, сам подбирает свободный слот; `not_before` из БД выводим в UI.
5. **Календарь** (неделя/день): слоты, перетаскивание ролика, «автозаполнение»: готовый ролик занимает ближайший свободный слот своих целей; блокировка дублей (один ролик — один аккаунт один раз).
6. **Профиль выхода на площадку**: длительность и битрейт под лимиты (`render_pool_copy` из `drafts.rs` — основа для «варианта под площадку»; «Часть N» убирается при нескольких аккаунтах — правило сохраняем).
7. **Права и кредит** (в профиле канала): `permission` (мой / по договорённости / не указано), строка кредита «Источник: …» автоматически в подписи, счётчик жалоб/ограничений на канал → автопауза канала после N событий; неуказанные каналы по умолчанию в режиме review.
- Проверка: для каждой площадки — поддельный сервер по образцу `tests/tiktok_e2e.rs` (куски, ретраи, лимиты, ошибки авторизации); юнит-тесты планировщика (окна через полночь, лимиты, ротация); живая проверка каждой площадки — **чек-пойнт с тобой** (аккаунты и ключи, см. ниже).

### Фаза 6 — Реклама и кампании (M–L)
- `campaigns`: рекламодатель, баннеры (несколько), ссылка, промокод, шаблон UTM (`utm_source=<площадка>`, `utm_content=<id ролика>`), даты, вес, лимиты (роликов в сутки/всего), фильтры по каналам и площадкам.
- **Ротация** — чистая функция `pick_banner(контекст, кампании, история)` (взвешенный круг с лимитами и датами, детерминированное зерно для тестов); результат пишется в `clip_campaigns` и в `banner_id` черновика (`drafts.rs::build_job`). Предпросмотр «следующие 10 роликов получат: …».
- **Подпись**: ссылка/промокод вставляются в подпись по шаблону платформы (в подписях, где ссылки не кликабельны, — текстом/промокодом).
- **Библиотека баннеров**: проверка ключа (доля «зелёных» пикселей в углах, длительность), поддержка баннеров с альфой (PNG/WebM) кроме хромакея.
- **Отчёт для рекламодателя**: по кампании — ролики (площадка, аккаунт, дата, ссылка), метрики (из Фазы 7), экспорт **HTML (самодостаточный, с превью) + CSV**; PDF — печать из webview.
- Проверка: юнит-тесты ротации (лимиты, истечение кампании, пустой пул), тест вставки ссылки/UTM, снимок отчёта.

### Фаза 7 — Аналитика и обратная связь (M–L)
- `metrics` (временной ряд) и сборщики по возможностям: YouTube (`videos.list` statistics), Instagram (insights), VK (`video.get`), TikTok (Display API, если приложение пройдёт аудит; иначе пропуск), Telegram — только то, что доступно боту, остальное вручную.
- Дашборд: опубликовано, просмотры, медиана, лучшие/худшие ролики, часы публикации, процент ошибок, «требует внимания».
- **Обратная связь в отбор**: для каждого момента храним вектор признаков (сигналы, оценки LLM, длина, час, шаблон) и исход (просмотры за 48 ч, нормированные на медиану аккаунта). После ≥50 роликов на канал показываем **подсказки** («поднять вес чата с 0,15 до 0,3»), применяешь **сам** — без молчаливых автоизменений.
- Уведомления рабочего стола о сбоях/капче/исчерпанной квоте.
- Проверка: юнит-тесты нормировки и подсказок на синтетических данных, моки API.

### Фаза 8 — Надёжность и эксплуатация (M)
- **Блокировка сна ПК**, пока фабрика в работе (Linux: логин-D-Bus inhibit / `systemd-inhibit`), переключатель «продолжать при запуске», опциональный трей и автозапуск.
- Экран «Диск»: политика хранения, использование по каналам, очистка.
- Идемпотентность публикаций (никогда не выкладывать дважды: внешний id + состояние `needs_check`, как уже сделано для TikTok, обобщить).
- Охрана видеопамяти: проверка совместной работы LLM + NVENC на 4 ГБ, автооткат на CPU; бенчмарк-набор (3-часовой VOD, 10 одновременных черновиков).
- Журналы и «пакет диагностики»; обновить `README`, пользовательскую инструкцию и `PKGBUILD`; версии 0.4.0 … 1.0.0 по вехам. Установщик Windows исключён по уточнению пользователя.

## Сквозные правила
- **Тесты**: чистые функции — юнит-тесты; каждая внешняя интеграция — с поддельным сервером/утилитой по образцам в `src-tauri/tests/`; тяжёлое с моделями — `#[ignore]`; `cargo test`, `npx tsc --noEmit`, `npm run build` зелёные на каждом шаге.
- **Проверка в окне**: изолированный запуск с `HOME`/`XDG_DATA_HOME` в scratchpad, отладочные маршруты `/dev/*`, скриншоты `/dev/snapshot`; не трогать установленное у тебя приложение и его процессы.
- **Не делаем**: антидетект-браузеры, подмену отпечатков, ротацию прокси для обхода блокировок, обход капчи (остаётся «пауза и ждём человека»), обход закрытых/платных/DRM-записей, внешние облачные ИИ-сервисы (всё локально, как решено).
- **Риск прав и платформ**: нарезка чужого контента может приводить к жалобам/блокировкам и к ограничениям монетизации у площадок. Смягчаем встроенными мерами (реестр разрешений, автокредит источника, трансформация: субтитры/раскладка/баннер, счётчик жалоб с автопаузой канала, режим review по умолчанию для каналов без разрешения), но решение, какой контент брать, остаётся за тобой.
- **Версии/релиз**: PR → merge-коммит → тег → `gh release create` — как раньше; релизы собираются по твоему слову.
